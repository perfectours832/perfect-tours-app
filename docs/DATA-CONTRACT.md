# חוזה נתוני מסלול

## גבולות השינוי

הגרסה הבסיסית ממשיכה לשמור את המסלול בעמודת `trips.itinerary` הקיימת באמצעות מנגנון השמירה של האפליקציה. אין טבלאות חדשות, אין מיגרציה ואין המרה גורפת של נתוני לקוחות. טיפוס JSONB בעמודה הוא הנחה מהקוד הקיים, ולא ממצא מאומת מסכמת Supabase. יש לאמת שמירה וטעינה בחשבון בדיקה ובסביבת בדיקה לפני פרסום.

מודל הנתונים נפרד מהתצוגה ומהעורך. הרשאות, שיוך סוכנות וחשיפת מסלול ציבורי נשארים באחריות השרת.

## הייצוג הנשמר

מסלול מובנה נשמר כמערך שטוח של רשומות פעילות. כל רשומה מציינת לאיזה יום היא שייכת. נשמרת תאימות לשדות המקוריים `day`, `time`, `title`, `description`.

| שדה | משמעות |
| --- | --- |
| `activity_id` | מזהה יציב של הפעילות. נוצר לפעילות חדשה; אינו מזהה הזמנה אצל ספק. |
| `day_id` | מזהה יציב של היום המשותף לפעילויותיו. |
| `day` | כותרת יום לתצוגה, למשל `יום 1 — רומא`. |
| `day_date` | תאריך מקומי בפורמט `YYYY-MM-DD`, אם הוזן. אין להסיק ממנו אזור זמן. |
| `time` | שעת פעילות מומלצת, בפורמט `HH:mm` כשמוזנת שעה מובנית. |
| `title` | שם הפעילות. |
| `description` | תיאור חופשי, כולל שורות חדשות ותווי `|` ללא פיצול לשדות. |
| `duration_minutes` | מספר שלם ולא שלילי של דקות, אם ידוע; מחרוזת ריקה מייצגת משך שלא הוזן. `null` קיים נשמר אם המסלול כולו לא נערך; שמירה מובנית לאחר עריכת המסלול מנרמלת אותו למחרוזת ריקה. |
| `address` | כתובת טקסטואלית. |
| `ticket_purchased` | ערך בוליאני המתאר כרטיס שנרכש מראש. אינו מחייב את הלקוח לבצע את הפעילות. |
| `entry_time` | שעת כניסה מחייבת, אם קיימת. נפרדת מהשעה המומלצת. |
| `reservation_status` | אחד מהערכים `""`, `not_booked`, `pending`, `confirmed`, `cancelled`. אינו דיווח ביצוע של הלקוח. ערך ישן אחר אינו מומר בשקט. |
| `image_url` | קישור HTTP/HTTPS לתמונת הפעילות, אם קיים. |
| `map_url` | קישור HTTP/HTTPS לניווט, אם קיים. |
| `document_url` | קישור HTTP/HTTPS לכרטיס או למסמך הקשור לפעילות, אם קיים. אינו יוצר הרשאת הורדה. |

יום ריק נשמר באמצעות רשומת סמן עם `kind: "day"`, השדות `day_id`, `day` ו־`day_date` לפי הצורך. הסמן אינו פעילות ואין להציגו ככרטיס אטרקציה. אם נטען סמן קיים, שדותיו הנוספים נשמרים גם לאחר הוספת פעילויות ליום; המודל מחזיק מידע זה ב־`_marker` בזיכרון.

סדר המערך שומר את סדר הימים והפעילויות שהסוכן קבע בעורך. תצוגת לקוח יכולה להציג את פעילויות היום כרונולוגית לפי השעה המומלצת, בלי לשנות את הנתונים השמורים. אין להסיק ביצוע רק משום ששעה חלפה. יש לשמור על מזהי פעילות ויום בעת עריכה וסידור מחדש.

ברשומות ישנות שאין להן מזהים, המודל יכול ליצור מזהי תצוגה דטרמיניסטיים לפי מיקום. יצירתם בזיכרון אינה אישור לכתוב אותם לשרת. לפעילויות וימים חדשים נוצרים מזהים חדשים; שינוי מזהי תצוגה ישנים נשמר רק כחלק מעריכה מפורשת של המסלול.

דוגמה לנתוני בדיקה מפורשים בלבד:

```json
[
  {
    "activity_id": "test-activity-1",
    "day_id": "test-day-1",
    "day": "יום 1 — נתוני בדיקה",
    "day_date": "2026-12-01",
    "time": "09:00",
    "title": "פעילות בדיקה",
    "description": "תיאור בשתי שורות\nהערה עם תו | נשמרת כחלק מהתיאור",
    "duration_minutes": 90,
    "address": "כתובת בדיקה",
    "ticket_purchased": true,
    "entry_time": "09:30",
    "reservation_status": "",
    "image_url": "",
    "map_url": "",
    "document_url": ""
  },
  {
    "kind": "day",
    "day_id": "test-day-2",
    "day": "יום 2 — יום ריק לבדיקה",
    "day_date": "2026-12-02"
  }
]
```

## נתונים קיימים והמרה בטוחה

1. טעינה אינה פעולת שמירה. אין לעדכן את Supabase בזמן הצגת מסלול.
2. שינוי שם לקוח, מלון או שדה חופשה אחר אינו אישור להמיר את המסלול. אם המסלול לא נערך, שומרים את הערך המקורי שלו ללא מעבר דרך פורמט הטקסט הישן.
3. נתונים מובנים קיימים מוצגים באמצעות התאמה למודל התצוגה. שדות חסרים אינם סיבה לנחש שמדובר בכמה פעילויות או שכרטיס נרכש.
4. טקסט חופשי או מבנה לא מוכר נשמרים כמקור. אין לחלק כל שורה לפעילות באופן אוטומטי.
5. ייבוא טקסט הוא תהליך יזום של הסוכן עם תצוגה מקדימה, בדיקת ימים ושעות ואישור לפני החלפת המסלול בעורך. האישור בעורך אינו כתיבה לשרת; השמירה נעשית באמצעות טופס החופשה.
6. נתונים שכבר פוצלו בצורה שגויה אינם ניתנים לתיקון ודאי באמצעות ניחוש. יש לבדוק ולתקן אותם בעורך לאחר השוואה למקור.
7. אין להשליך שדות לא מוכרים באופן שקט בעת עריכת מסלול קיים. אם לא ניתן לשמר מבנה, יש לחסום המרה שקטה ולהציג את המקור לסקירה.

## הבחנות עסקיות

`time` הוא זמן מומלץ; `entry_time` הוא זמן כניסה מחייב; `reservation_status` מתאר הזמנה; `ticket_purchased` מתאר רכישת כרטיס. אף אחד מהשדות אינו מצב ביצוע בפועל.

בעתיד דיווחי `בוצע`, `דולג` ו־`נדחה` יישמרו בנפרד מהמסלול הרשמי, עם הקשר ללקוח ול־`activity_id`. ללא דיווח מפורש המצב יהיה `לא דווח`. דילוג לא יבטל הזמנה ולא ייצור זכות אוטומטית להחזר. רק הסוכן ישנה את המסלול הרשמי.

## הכנה לריבוי סוכנויות

אין לבסס הרשאות על מזהים או סינון ב־JavaScript. השלב המסחרי ידרוש שיוך מסלולים ומסמכים לסוכנות, חברות משתמשים בסוכנות, RLS, RPC ציבורי בעל חשיפה מצומצמת ומיתוג לפי הסוכנות של החופשה. יש לתכנן מיגרציה נפרדת עם גיבוי ובדיקת בידוד נתונים לפני הפעלתה.
