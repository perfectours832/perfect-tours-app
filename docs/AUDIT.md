# בדיקת הפרויקט — Perfect Tours

## היקף והגבלות

הבדיקה התחילה מהקוד הקיים במאגר, ב־commit `2489f6a`, וכללה את קובצי המקור, ההיסטוריה, רשימות התוכן של שני קובצי ה־ZIP והשוואת דף השורש לאתר הקיים. דף השורש שנבדק באתר תאם לגרסת `index.html` במאגר. התאמה זו אינה מוכיחה ששאר קובצי האתר או הגדרות Netlify זהים למאגר.

לא בוצעו שינויים בבסיס הנתונים, לא שונו לקוחות אמיתיים, לא נשלחו הודעות ולא בוצעה פריסה. אין במאגר סכמה, מיגרציות או הגדרות RLS ו־RPC של Supabase. לכן תיאור בסיס הנתונים במסמך זה הוא הסקה מהקוד; הרשאות, טיפוסי עמודות והתנהגות פונקציות השרת לא אומתו.

## מפת הקוד המקורי

| קובץ | תפקיד וממצא בבדיקה הראשונית |
| --- | --- |
| `index.html` | נקודת הכניסה העובדת. מכילה ממשק סוכן וממשק לקוח, CSS ו־JavaScript פנימיים. פרמטר `?trip=` בוחר בממשק הלקוח. |
| `index-new.html` | עותק מוקדם של האפליקציה, עם כפילות בלוגיקה ובעיצוב וללא הרחבות הכרטיסיות והעורך. |
| `admin.html` | ממשק ישן המפנה לקובצי `config.js`, `app.js`, `admin.js` שאינם קיימים בגרסה המקורית במאגר. |
| `client.html` | ממשק ישן המפנה לקובצי `config.js`, `app.js`, `client.js` שאינם קיימים בגרסה המקורית במאגר. |
| `client-cards-v1.js` | שכבת תיקון העוטפת פונקציות גלובליות לניתוח, כתיבה והצגת המסלול ומזריקה CSS נוסף. |
| `trip-editor-v1.js.` | קובץ עורך ששמו מסתיים בנקודה. `index.html` מבקש `trip-editor-v1.js` ללא הנקודה, ולכן העורך אינו נטען כפי שנשמר במאגר. |
| `styles.css` | עיצוב הממשקים הישנים; דף השורש המקורי השתמש בעיקר בסגנונות פנימיים. |
| `password.html` | מסך עצמאי לאיפוס ושינוי סיסמה באמצעות Supabase. קישורי החזרה שלו מפנים ל־`admin.html` הישן. |
| `sw.js` | רישום Service Worker ללא מנגנון מטמון או תמיכה במצב לא מקוון. |
| `manifest.webmanifest` | מופיע בקישורי HTML אך אינו קיים במאגר המקורי. |
| קובצי ZIP | עותקי HTML ותיקוני סיסמה ישנים בלבד; אינם מכילים את קובצי JavaScript החסרים או סכמה. |

ההיסטוריה אינה מכילה את קובצי JavaScript החסרים. גם commit שכותרתו `manifest.webmanifest` אינו מוסיף קובץ כזה; הוא מוסיף אייקונים וכולל JSON של manifest בהודעת ה־commit.

## גורמי התקלות

1. **פיצול פעילות לכרטיסיות:** פונקציית `parseLines` המקורית מניחה שכל שורה היא פעילות ושכל שורה בנויה בדיוק כך: `יום | שעה | כותרת | תיאור`. טקסט חופשי רב־שורות מפוצל לרשומות ללא הבנה של המבנה המקורי. הרחבת הכרטיסיות יוצרת כרטיס גם לרשומה חסרת כותרת, ולעיתים משתמשת בשדה היום ככותרת. כך שעה, שם והערה עלולים להופיע בנפרד. אין די מידע כדי למזג אוטומטית רשומות שכבר נשמרו באופן שגוי.
2. **אובדן פרטים בעריכה:** מעבר הלוך ושוב דרך טקסט מופרד ב־`|` אינו שומר בבטחה תיאורים רב־שורתיים, תווי `|` ושדות שלא נכללו ברשימת השדות של הממיר. שינויים בפרטי החופשה עלולים לגרור כתיבה מחודשת של המסלול גם בלי כוונה לערוך אותו.
3. **עורך שאינו זמין:** שם קובץ העורך וקישור הטעינה אינם זהים. בנוסף, העורך הקודם תלוי בשכבות עיטוף של פונקציות ובסדר טעינה.
4. **עיצוב לא אחיד:** נוספו כמה שכבות CSS, כולל שכבת עיצוב לפני `<head>`, סגנונות פנימיים וסגנונות שמוזרקים מתוך JavaScript. חלק מהכללים סותרים זה את זה. כותרות, אזור פתיחה וריווחים גדולים מצמצמים את שטח המסלול במסך טלפון.
5. **כמה נקודות כניסה שונות:** העותקים והעמודים הישנים אינם משתמשים באותה לוגיקה. קישור ל־`admin.html` או ל־`client.html` אינו מבטיח את התנהגות דף השורש.
6. **ערבוב הזמנה ותזמון:** סימון כרטיס שנרכש הציג גם משמעות של שעת כניסה חשובה. רכישת כרטיס, שעת פעילות מומלצת ושעת כניסה מחייבת הם נתונים נפרדים.

## חיבור Supabase הקיים

הסוכן מתחבר באמצעות `auth.signInWithPassword`; טעינת ההתחברות משתמשת ב־`getSession` וב־`onAuthStateChange`. המסלול נשמר בטבלת `trips` באמצעות `insert` או `update` לפי `id`. העמוד משתמש ב־`business_settings` להגדרות העסק.

לקוח מקבל מסלול דרך `get_public_trip({ lookup_public_id })` והגדרות דרך `get_public_settings()`. קישור ציבורי חדש נוצר באמצעות 16 בתים אקראיים של `crypto.getRandomValues`. זהו קישור גישה למחזיק בקישור; אין בקוד מנגנון התחברות של לקוח.

הקוד מתייחס אל `itinerary` ו־`documents` כמערכים. ייצוג JSON/JSONB הוא הנחה סבירה מהשימוש, אך לא נבדק מול סכמת השרת. אין להפעיל SQL או לשנות טיפוס עמודה על בסיס ההנחה הזאת.

בוצעה גם בקשת מטאדאטה בלבד ל־`/rest/v1/` עם המפתח הציבורי הקיים. השרת החזיר `401` עם ההודעה `Secret API key required`, ולכן תיאור OpenAPI לא היה זמין בהרשאה זו. לא התבקשו רשומות לקוחות, לא הופעל RPC ולא נעשה ניסיון להשתמש במפתח סודי. תגובה זו אינה מוכיחה שקריאות המסלול הרגילות נכשלות; היא מגבילה את אימות הסכמה.

## אבטחה והרשאות

- הצגת מסמכים ומלון בקוד המקורי אינה בודקת פרוטוקול URL. HTML escaping אינו חוסם `javascript:`. נדרש סינון HTTP/HTTPS משותף לקישורי מפות, תמונות ומסמכים, לצד הגנות לפתיחה בחלון חדש ומדיניות referrer.
- אין בקוד תהליך להעלאת מסמכים פרטיים או לקבלת קישורים חתומים. סינון URL אינו מגביל מי רשאי להוריד את המסמך בשרת שמארח אותו.
- יצירת חופשה בקוד המקורי אינה שולחת `owner_id` או `agency_id`; ייתכן שהבעלות נקבעת בשרת, אך הדבר לא אומת.
- `get_public_settings()` אינו מקבל מזהה חופשה או בעלים. נדרש בעתיד לקשור מיתוג והרשאות לסוכנות של החופשה בצד השרת.
- קיים ערך `draft` בממשק. לא ניתן לדעת מהמאגר אם `get_public_trip` מסתיר טיוטות. יש לאמת זאת בחשבון בדיקה לפני שחרור.
- גבול ההרשאות חייב להיות ב־Supabase: RLS, חברות בסוכנות, מדיניות מסמכים ו־RPC מצומצמים. סינון בממשק אינו גבול אבטחה.

## מבנה התיקון

נקודת כניסה אחת ב־`index.html`, לוגיקת אפליקציה ב־`app.js`, מודל מסלול משותף ב־JavaScript רגיל, קובצי תצוגה ועורך נפרדים וסגנונות חיצוניים. העמודים הישנים מפנים לנקודת הכניסה הקנונית תוך שמירת הקישורים הרלוונטיים. נשמרים מנגנון האימות ופעולות השמירה הקיימים; אין מיגרציה של Supabase.

ממשק הלקוח מציג ימים וכרטיסיות קומפקטיות נפתחות. העורך מציג ימים ופעילויות מובנים ושומר באותה עמודת מסלול. מסלול קיים שלא נערך נשמר כפי שנטען. טקסט ישן אינו מומר אוטומטית: המרה דורשת תצוגה מקדימה ואישור מפורש של הסוכן. חוזה הנתונים מתועד ב־[DATA-CONTRACT.md](DATA-CONTRACT.md).

בקשות שינוי, דיווחי ביצוע/דילוג/דחייה, דירוגים, דוחות יומיים והתראות דורשים שלב פיתוח נוסף לאחר אישור הגרסה הבסיסית. אין להציג אותם כפעולות פעילות ללא שמירה אמיתית בצד השרת.

בדיקות ההפצה שנותרו תלויות בסכמת Supabase ובחשבונות בדיקה מפורטות ב־[RELEASE-CHECKLIST.md](RELEASE-CHECKLIST.md).
